# YouTube Transcript Flow — Component Contract

## Architecture

```
┌─────────────────┐     window.postMessage     ┌──────────────────────┐
│  MAIN world     │ ◄────────────────────────► │  Isolated world      │
│  (bridge)       │     cpdown namespace       │  (content script)    │
└─────────────────┘                            └──────────┬───────────┘
                                                           │
                                                   chrome.runtime.sendMessage
                                                           │
                                                           ▼
                                                  ┌──────────────────┐
                                                  │  Background SW   │
                                                  │  (entrypoints/   │
                                                  │   background.ts) │
                                                  └──────────────────┘
```

## 1. Components

### MAIN-world bridge (`entrypoints/content.ts` or separate MAIN-world entry)
- **Responsibility:** Observe network responses (fetch + XMLHttpRequest) for YouTube
- **Allowed:** window, fetch, XMLHttpRequest, postMessage
- **Forbidden:** chrome.* (not available in MAIN world), DOM clicks, CC button manipulation
- **Output:** sends typed `cpdown` messages via `window.postMessage`

### Isolated-world client (`entrypoints/content.ts` or separate content script)
- **Responsibility:** Communicate with MAIN-world bridge, select caption track, fetch timedtext, send result to background
- **Allowed:** chrome.runtime.sendMessage, fetch, DOM reading
- **Forbidden:** accessing ytInitialPlayerResponse directly (only via bridge), CC button clicks

### Background service worker
- **Responsibility:** Register context menu, handle toolbar clicks, route transcript results to toast
- **Allowed:** chrome.* APIs

## 2. Message Protocol (MAIN ↔ Isolated)

### Message types

#### `BRIDGE_READY`
MAIN → Isolated. Signals the bridge is installed and listening.

```ts
{
  channel: string;      // unique per-session channel ID
  type: "BRIDGE_READY";
  navigationId: string; // current page navigation
  videoId: string;      // current video ID from URL
}
```

#### `PLAYER_RESPONSE`
MAIN → Isolated. Contains extracted player data.

```ts
{
  channel: string;
  type: "PLAYER_RESPONSE";
  requestId: string;
  navigationId: string;
  videoId: string;
  payload: {
    videoId: string;
    captionTracks: Array<{
      baseUrl: string;
      languageCode: string;
      languageName: string;
      kind?: string;
      isTranslatable: boolean;
    }>;
  } | null;  // null if no caption data found
  pot: string | null;
}
```

#### `TIMEDTEXT_URL`
MAIN → Isolated. Captures timedtext URL with pot.

```ts
{
  channel: string;
  type: "TIMEDTEXT_URL";
  navigationId: string;
  payload: { url: string };
}
```

### Channel and requestId

- `channel` — unique random string generated once per content script session. All messages must have channel === current channel to be accepted.
- `requestId` — unique per-request ID generated by the isolated-world client. Only responses with matching requestId are accepted.
- `navigationId` — derived from the current URL or SPA state. Messages from stale navigation are rejected.

## 3. Data flow

```
1. Page loads with YouTube video
2. ✅ MAIN-world bridge installs itself (if not already installed)
3. ✅ MAIN-world bridge sends BRIDGE_READY to isolated world
4. ✅ Isolated world receives BRIDGE_READY, stores channel + navigationId + videoId
5. (Optional) Isolated world sends GET_PLAYER_DATA request
6. ✅ MAIN-world bridge intercepts youtubei/v1/player response, extracts captionTracks, sends PLAYER_RESPONSE
7. ✅ Isolated world receives PLAYER_RESPONSE, selects best track via selectTrack()
8. ✅ Isolated world fetches timedtext from selected track's baseUrl + pot
9. ✅ Isolated world parses SRT to plain text
10. ✅ Isolated world sends result to background via chrome.runtime.sendMessage
```

## 4. Sensitive data — NEVER log or store

- Video URL (entire URL or search params)
- Video title
- Transcript/subtitle text
- Auth tokens, cookies
- Full network responses
- pot parameter (can be short-lived but not for diagnostics)

Allowed in diagnostics: DiagnosticCode, area, occurredAt, counter values.

## 5. Timeouts

| Phase | Timeout | Notes |
|---|---|---|
| Waiting for PLAYER_RESPONSE | 8 seconds | Single attempt for initial data |
| Retry after SPA navigation | 8 seconds | Max 1 retry |
| Fetch timedtext | 10 seconds | One attempt |
| Total per request | ~18 seconds | Client should show progress or early error |

## 6. Error conditions and codes

| Condition | DiagnosticCode | User message | Technical cause |
|---|---|---|---|
| No caption tracks in player response | YOUTUBE_NO_CAPTIONS | No captions available for this video | playerResponse.captions missing or empty |
| Track selection returned null | YOUTUBE_TRACK_NOT_FOUND | Could not find a suitable caption track | AllCaptionTrack list is empty or all tracks filtered out |
| Player response timeout | YOUTUBE_PLAYER_TIMEOUT | Could not get caption data in time | 8s timeout expired |
| Timedtext fetch failed | YOUTUBE_TIMEDTEXT_REQUEST_FAILED | Could not download captions | Network error or non-OK HTTP status |
| Timedtext body is empty | YOUTUBE_TIMEDTEXT_EMPTY | Downloaded captions are empty | HTTP 200 with zero-length body |
| Stale video/navigation ID | YOUTUBE_STALE_RESPONSE | Received data belongs to a different video | navigationId/videoId mismatch |
| Invalid bridge message | YOUTUBE_BRIDGE_INVALID_MESSAGE | Internal communication error | Message missing required fields or wrong type |

## 7. Preventing stale data

- Each content script session generates a unique `channel` string
- Each transcript request generates a unique `requestId`
- The isolated client tracks the current `navigationId` (derived from `location.href` via `hash + search + pathname`)
- Messages from a different `navigationId` are silently dropped
- Messages from a different `videoId` are silently dropped
- Messages with a mismatched `requestId` are silently dropped
- After receiving a valid response, all listeners and timers are cleaned up

## 8. No-CC-click guarantee

- The MAIN-world bridge NEVER calls `.click()`, `.dispatchEvent()`, or `new MouseEvent()` on any DOM element
- The MAIN-world bridge NEVER queries for CC button selectors (`.ytp-subtitles-button`, etc.)
- The isolated-world client NEVER accesses the YouTube player DOM for caption data
- The only data source is network interception + typed bridge messages
